# Qommons AI 利用状況レポート(自動実行)

Claude の定期タスク(Routine)が2種類動いており、いずれも以下を行います。

1. Qommons AI にメール+パスワードでログイン(Playwright によるブラウザ自動操作)
2. **集計前に登録者マスタ(`registrants.csv`)を最新化**
3. 利用者ログ(QuickSight ダッシュボード)から対象期間の利用ログ CSV をダウンロード
4. CSV を集計して Markdown レポートを生成
5. `build_report.py` で「QommonsAI利用集計.xlsx」形式の詳細集計ブックを再構築
   (`reports/QommonsAI利用集計_YYYY-MM.xlsx` として保存、直近に生成した月は
   リポジトリ直下の `QommonsAI利用集計.xlsx` にも複製)
6. このリポジトリ(非公開)の `main` にコミット・プッシュし、要点をプッシュ通知・ファイル送付

## 定期実行スケジュール

| Routine | 実行タイミング | 対象期間 | 出力レポート |
|---|---|---|---|
| 週次 | 毎週日曜 8:00 JST | 当月1日〜当日 | `reports/YYYY-MM-DD.md` |
| 月次 | 毎月1日 8:00 JST | **前月1日〜前月末日** | `reports/YYYY-MM_月次まとめ.md` |

- 週次は 2026年8月から「毎朝」→「毎週日曜のみ」に変更(2026-07-31 ユーザー指示。
  平日・土曜は実行しない)
- 月次は 2026年9月から追加(2026-08-30 ユーザー指示)。前月分の確定データを
  部局別・話題別・前月比まで踏み込んでまとめる
- 月次 Routine の cron は `0 23 28-31 * *`(UTC)。標準の5フィールド cron では
  「月末日」を表現できないため月末28〜31日に発火し、**プロンプト冒頭で JST の
  日付が1日かどうかを判定**して、1日でなければ何もせず終了する
- 月初1日の週次と月次が重なることはない(週次は日曜のみ)。月次実行の直後に
  週次が走る場合、週次は当月分(数日分)を対象にするため前月末日は含まれないが、
  前月末日のデータは月次まとめで確定値として取得済み

## 実行環境の前提

Claude Code on the web の環境(Environment)設定:

| 項目 | 内容 |
|---|---|
| ネットワーク | `qommons.ai` と QuickSight(`*.quicksight.aws.amazon.com`)に到達できること(フルアクセスで可) |
| `QOMMONS_EMAIL` | ログイン用メールアドレス(環境変数) |
| `QOMMONS_PASSWORD` | パスワード(環境変数) |
| `QOMMONS_URL` | (任意)ログインページ URL。既定は `https://qommons.ai/login` |

認証情報はリポジトリ・レポート・ログには一切書き込みません。
利用ログ CSV(職員の発話内容を含む)もコミットしません(`.gitignore` 済み)。

## 手動実行

```sh
npm init -y && npm i playwright   # 初回のみ(ブラウザ本体はプリインストール済み)
node fetch_registrants.mjs        # 登録者マスタの更新(集計前に必ず実行)
python3 update_registrants.py     # → registrants.csv を再生成
node fetch_logs.mjs
```

成功すると `downloads/qommons-log-YYYY-MM-DD.csv` が保存されます。
失敗時は `debug/` にスクリーンショットとページ HTML が残ります。

## 登録者マスタの更新(集計作業の前に必ず実行する)

**2026-08-07 ユーザー指示**: 定期作業(集計)の前に、必ず登録ユーザーを最新化すること。
アカウント整理(削除・追加・異動)が随時行われるため、古いマスタのままだと
部署別集計の登録者数・利用率がずれ、所属不明の利用者が「(未登録)」に
集計されてしまう。

```sh
node fetch_registrants.mjs      # 組織管理のメンバー一覧を Excel でダウンロード
python3 update_registrants.py   # registrants.csv を再生成(差分を標準出力に表示)
```

`fetch_registrants.mjs` の実機確認済みフロー(2026-08-07):

1. `/login` でログイン(入力欄は `pressSequentially` で1文字ずつ入力する。
   `.fill()` だと React 側の onChange が発火せず、ログインボタンが disabled のままになる)
2. 画面左下のアカウントメニュー(部署名表示)をクリック → 「組織管理」→ `/management`
3. 右上「管理」ボタン → 「メンバー登録」→ モーダル内の
   「ダウンロード：20,000件テンプレート」リンク

ダウンロードされる Excel は名前こそ「テンプレート」だが、**現在の登録メンバー全員が
事前入力された状態**で入っており、`registrants.csv` と同じ項目(ログインID・氏名・
カナ・アクセスレベル・部署名・本パスワード設定状況)がそのまま取得できる。
この Excel は氏名を含むためコミットしない(`.gitignore` 済み)。

## 実機確認済みのフロー(2026-07-20)

1. `/login`: `input[name=username]` / `input[name=password]` → 「ログイン」ボタン(CAPTCHA・2FAなし)
2. `/log-dashboard`(利用者ログ)は Amazon QuickSight の iframe 埋め込み。
   iframe 内からのダウンロードはヘッドレスで検知できないため、埋め込み URL を
   リクエスト横取りで取得し、トップレベルページとして開く
3. Controls 展開 → `input[aria-label="Enter a date"]` ×2 に開始日・終了日を入力
4. 「利用ログ」テーブルにホバー → `[aria-label="Menu options, 利用ログ, Table"]`
   → 「Export to CSV」

CSV の列: `ユーザー名, 利用日時, ai_name_new, model_name, 入出力内容`

## リモート実行環境向けの対応(スクリプトが自動処理)

- 外向き HTTPS はプロキシ経由 → Chromium にプロキシを明示指定
- プロキシの TLS 再終端 → CA を NSS ストアへ毎回登録(libnss3-tools を自動インストール)
- プロキシが Chromium の TLS1.3 ClientHello を処理できない → TLS1.2 上限を指定

## 詳細集計ブック(QommonsAI利用集計.xlsx)の自動再構築

`build_report.py` は、2026-07-20 にユーザーから提供された既存の集計ブック
(「利用ログ.xlsx」から手動生成されていたもの)と同じ構成を、生ログ CSV +
登録者マスタから機械的に再現する。

```sh
pip install openpyxl janome scikit-learn   # 初回のみ
python3 build_report.py [CSVパス]   # 省略時は downloads/ の最新ファイル
```

### 使うファイル

| ファイル | 役割 |
|---|---|
| `registrants.csv` | メール(またはメール未登録者の職員番号)↔氏名・部署の登録者マスタ。HRの異動があれば手動で更新する |
| `report_settings.json` | 業務削減効果試算の前提値(人件費・労働時間など)。編集可 |
| `reports/QommonsAI利用集計_YYYY-MM.xlsx` | 生成される月次の集計ブック(コミット対象) |
| `QommonsAI利用集計.xlsx` | 常に最新月を指す複製(デスクトップに保存する際はこれを使う) |

### 再現できているシート(2026-07-20 に実データで検証済み、既存ファイルとの誤差1%未満)

部署別集計・個人別集計(削減時間含む)・課別文字数TOP3・対応表・
モデル/機能別集計・時間帯/曜日別集計・利用者推移・入出力の文字数分布/
ファイル添付率/機能別平均文字数・業務削減効果_試算(下記セッション定義含む)。

個人別「削減時間」の式: `(入力文字数×0.012分 + 出力文字数×0.002分) ÷ 60` [時間]
(実データから逆算して確認済み)。

業務削減効果_試算の「１つの文脈での質問数(C)」は `update_shukei.py` と同じ
セッション分割ロジックで自動算出する(ユーザー提供、2026-07-20):
1. ユーザー発言行(`入出力内容` が `user#` で始まる行)だけを抽出
2. ユーザーごとに時系列に並べ、直前発言との時間差を計算
3. 時間差が `session_gap_minutes`(既定60分、`report_settings.json` で変更可)を
   超える、または最初の発言 → 新セッション開始とみなす
4. `C = 総プロンプト数 ÷ セッション数`

実データ(7/1〜7/20)で C=4.104(参照ファイルの7/1〜7/19時点の値4.109とほぼ一致)。

### メールアドレスを持たない職員(職員番号ログイン)の扱い

登録者マスタの一部の行はメールアドレスが空で、代わりに `employee_no` 列に
6桁の職員番号が入っている(2026-07-22 ユーザー提供)。生ログの `ユーザー名`
列では、これらの職員は `<職員番号>@北海道_函館市` という形式のログインIDで
記録される。`load_registrants()` はメールが空の行をこの形式のキーで登録し、
生ログと突き合わせて氏名・部署を解決する(以前はメール空欄の行を丸ごと
スキップするバグがあり、該当職員が軒並み「(未登録)」扱いになっていた。
2026-07-22 に修正)。

### 対応表の列(registrants.csv)

`email, employee_no, name, name_kana, access_level, department, status` の
7列。`access_level`(メンバー/管理者)と `status`(完了/未完了)は 2026-07-22
に追加された列。`status`=「未完了」はアカウント発行済みだがまだ利用を
開始していない登録者を指す(ユーザー確認済み)。

部署別集計シートの「登録者数」は **全体** と **利用開始済み(status=完了)**
の2列を併記する。「利用率」は **登録者数(全体)** を分母に計算する
(2026-07-23 ユーザー指示。一時的に利用開始済みを分母にしていたが変更)。

### 週次推移(weekly_trend.py)

**2026-09-06 ユーザー指示**: 定時レポートに週次推移を載せること。

レポート本体の数字は「月初からの累計」なので、月をまたぐと前週と単純比較できない
(例: 8/30時点646人 vs 9/6時点522人は期間長が違う)。そこで月曜〜日曜の週単位で
切り直した推移を `weekly_trend.py` で算出し、レポートに併記する。

```sh
python3 weekly_trend.py            # 履歴を更新して直近4週の表を出力
python3 weekly_trend.py --weeks 6  # 表示週数の変更
```

- `downloads/` は .gitignore 済みでコンテナ再作成時に消えるため、**週ごとの集計値のみ**
  を `weekly_stats.json` としてコミットして引き継ぐ(発話内容やログインIDは保存しない)
- CSVは毎回「当月1日〜当日」で取得するため複数ファイルが同じ日付を含む。件数は日付ごとに
  **最も件数の多いスナップショット**を採用して多重計上を防ぐ(利用者は和集合でよい)
- 「継続/新規/離脱」は連続する2週分の生ログが手元にある場合のみ算出する(集計値だけでは
  復元できないため、月初の実行などでは省略される)
- 定時実行は日曜朝のため最新週は日曜日中の利用を含まないが、毎週同条件のため比較に影響しない

### 新規/リピーターの判定(利用者推移シート)

`build_report.py` は当月分のCSVしか読まないため、素朴に実装すると月初の
利用者が全員「新規」に分類されてしまう(2026-08-19 ユーザー指摘)。

これを避けるため、`load_prior_month_users()` が
`reports/QommonsAI利用集計_YYYY-MM.xlsx`(当月より前の月)の「個人別集計」
シートを読み、**前月までに利用実績のあるログインIDを既知**として扱う。
前月までに使っていた人は月初からリピーターに計上される。

- 過去月のブックが無い期間は判定できないため、その分は従来どおり「新規」
  になる(運用初月の7月は全員新規で正しい)
- 「累計ユニーク」列は**当月内**の数字なので、過去月の利用者は含めない

### 頻出単語 Top30(入出力傾向分析シート)

janome(辞書同梱の純Python形態素解析ライブラリ、`pip install janome`)で
名詞のみを抽出して頻度集計する。助詞・助動詞・代名詞・数値・「こと」
「もの」などの機能的な名詞は除外している(2026-07-22、以前の単純な
N-gram部分文字列集計から変更。語尾の断片が上位に出てしまう問題を解消)。

### 主な話題・テーマ(新シート、2026-07-22 追加)

QommonsAI自体のダッシュボードにある「主に会話された分野・テーマ」相当の
機能。単純な単語頻度では文脈が分からないという要望を受けて追加した。

**自動処理(`build_report.py` 内、`cluster_topics()`)**:
1. ユーザー発言を名詞ベースでTF-IDFベクトル化(汎用語は追加ストップワードで除外)
2. TruncatedSVD(潜在意味解析)で次元圧縮 → KMeansで8分野にクラスタリング
3. 各分野の件数・割合・上位キーワードを自動集計してシートに書き込む
   (この部分は完全自動・決定的)

**手動処理(実行者が担当)**: 分野の「話題名」「概要」(1〜2文の説明)は
統計処理だけでは生成できないため、日次実行のたびに以下の手順で埋める。
1. `build_report.py` 実行後に生成される `debug/topics_for_labeling.json`
   (生の質問文サンプルを含むため `debug/` はコミット対象外)を読み、
   各クラスタのキーワードと代表的な質問例を確認する
2. 各クラスタに話題名・概要を執筆し、`labels.json`(例は `label_topics.py`
   冒頭のdocstring参照)として保存
3. `python3 label_topics.py labels.json` を実行し、既に生成済みの
   `reports/QommonsAI利用集計_YYYY-MM.xlsx` と `QommonsAI利用集計.xlsx` の
   「主な話題・テーマ」シートに話題名・概要を書き込む(再クラスタリングは
   行わないため、キーワード側と齟齬が出ない)

生の質問文サンプル自体はワークブックにもリポジトリにも一切残さず、
執筆した要約文だけをコミットする。

### 既知の制限(自動化できていない/近似の箇所)

- 添付ファイル付きプロンプトの入力文字数は、生ログのJSON構造から
  `message` フィールドを抽出して数えているが、既存ファイルとの数値差が
  ごく僅か(部署合計で1%未満)残っている。原因は未特定(添付関連の
  取り扱い方法の細部の違いと推測)。
- 登録者マスタ・生ログのいずれにも存在しないアカウント(退職者の残存ログ等)
  は部署「(未登録)」として集計される。`system@city.hakodate.hokkaido.jp` は
  総務部情報システム課として固定的に扱う。
